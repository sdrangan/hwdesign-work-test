# 16-QAM LLR demapper -- results

Vitis HLS kernel `qam16_llr`, built with Waveflow in the `stream_inband` frame: the
`stream_inband` reference design scaffolded with `waveflow_new_accel_project`, then adapted.
Part `xc7z020clg484-1`, 10 ns clock, Vitis HLS 2025.1, 32-bit stream words.

Rebuild everything with `python qam16_llr_build.py --through summary` (about 4 minutes).

## Interface

**Ports** (generated boundary, `gen/qam16_llr.cpp`): `s_in` and `m_out`, AXI4-Stream, 32 bits;
`halted`, `error`, `tx_id` and `ap_ctrl` on AXI-Lite bundle `control`.  The host writes only
`ap_start`.

**Command header** `Qam16LlrCmdHdr`, 2 words.  These layouts come from serializing instances
(see `layout.md`):

| Word | Bits | Field | Meaning |
| --- | --- | --- | --- |
| 0 | 7:0 | `cmd_type` | uint8: `DEMAP` = 0, `END` = 1, any other value is unknown |
| 0 | 23:8 | `tx_id` | uint16 |
| 0 | 31:24 | -- | sent as 0, ignored |
| 1 | 15:0 | `nsamp` | uint16, 1..1024 for DEMAP (0 and ignored for END) |
| 1 | 31:16 | `inv_var` | uint16, raw u8.8 (0 and ignored for END) |

**Sample burst** (after a DEMAP): `nsamp` words, TLAST on the last.  Each word holds one
complex sample (`ComplexField` over int16): `yI` in bits 15:0 and `yQ` in bits 31:16, each raw
s8.8.

**Response** to each DEMAP:
1. `Qam16LlrRespHdr`, 1 word: `tx_id` in bits 15:0 (31:16 are 0), with TLAST.
2. An LLR burst of `nsamp` words, TLAST on the last.  Each word holds the four int8 LLRs of one
   sample, raw s6.2: b0 in 7:0, b1 in 15:8, b2 in 23:16, b3 in 31:24.

There is no footer.  END gets no response.

**Status registers** (AXI-Lite, read-only, cleared at the start of every activation):
`halted` (1 bit), `error` (8 bits), and `tx_id` (16 bits: the `tx_id` of the command that
failed, 0 after a clean run).

**Error codes** (`Qam16LlrError`):

| Code | Name | Raised when | Output for the failing command |
| --- | --- | --- | --- |
| 0 | `NO_ERROR` | | |
| 1 | `TLAST_EARLY_SAMP_IN` | TLAST on sample word j < nsamp-1 | response header, then j+1 LLR words, TLAST on the last |
| 2 | `NO_TLAST_SAMP_IN` | the last sample word has no TLAST | response header, then all nsamp LLR words, TLAST on the last |
| 3 | `BAD_PARAM` | DEMAP with nsamp outside 1..1024 | nothing; no sample is read |
| 4 | `UNKNOWN_CMD` | `cmd_type` is neither 0 nor 1 | nothing; no sample is read |

On any error the kernel sets the status and returns at once, without reading more input.

## Design

- **Files.**
  - `qam16_llr.py`: schemas, `qam16_llr_eval` (the integer arithmetic), `qam16_llr_stream_model`
    (the whole protocol), the body-only `HostActivated` module with its pysim body, and the
    pysim testbench.
  - `scenarios.py`: intents, stimulus, the expected responses and the checker.
  - `qam16_llr_body_impl.tpp`: the hand-written C++ body.
  - `qam16_llr_tb.cpp`: the C++ testbench.
  - `qam16_llr_build.py`: the build graph.
  - `gen/` and `include/`: generated by Waveflow, not edited.  `include/wf_cint.h` is Waveflow's
    shipped header, copied in as `examples/schemas/complex` does.
- **Loop structure.**
  - `commands:` a `while(true)` loop.  Each pass reads one 2-word header and:
    - on END, returns;
    - checks `cmd_type`, then `nsamp`;
    - otherwise writes the response header and runs the sample loop.
  - `samples:` `for i < nsamp`, `PIPELINE II=1`.  Each iteration reads one sample word, computes
    the four LLRs, and writes one LLR word.  TLAST goes on the final word, or on the word whose
    input carried an early TLAST (then `break`).
- **Arithmetic.** Per axis:
  - `a = |y|` (ap_uint<17>), `d = 512 - a` (ap_int<18>);
  - `p = inv_var*y` (ap_int<33>) and `q = inv_var*d` (ap_int<35>), both exact;
  - `sat8((x + 8192) >> 14)`, using ap_int's arithmetic shift.
  - This uses 4 DSPs, one per product.
- **State.**
  - Kept: the status registers (AXI-Lite) and loop-local registers.
  - Not kept: anything between commands or activations.  `inv_var` and `nsamp` are read from
    each header.
  - No BRAM.
- **Throughput.** The sample loop is pipelined at II = 1, depth 5, and each sample is exactly
  one input word and one output word.  So once samples stream, the kernel takes one complex
  sample and emits its four LLRs every clock.
  - Fixed per-command overhead: the 2-word header, the response header, and the pipeline
    fill/drain.
  - In cosim, a 1024-sample command takes 1039 cycles from start to done.

## Assumptions

- **Stream width.** 32-bit words only, as frame F2 states.  The reference's 64-bit variant was
  dropped.
- **Command field.** `cmd_type` is an 8-bit integer field, not an `EnumField`.  A Waveflow enum
  cannot serialize a value that names no command, so an unknown-command scenario could not be
  built without packing words by hand.  Codes: DEMAP = 0, END = 1, and anything else is
  `UNKNOWN_CMD` (new error code 4).
- **Error codes.** 1 to 3 are kept from the frame (`BAD_PARAM` = 3 is nsamp out of range).
- **Status for an unknown command.** It reports the `tx_id` field of the unknown header.
- **Precedence.** Within one header, an unknown `cmd_type` is checked before `nsamp`.  Both
  checks happen before anything is written for the command.
- **END.** Its `nsamp` and `inv_var` are ignored.  Unused header bits are sent as 0 and ignored.
- **Response header.** It echoes only `tx_id` (prompt: "its response carries tx_id and the
  LLRs").  There is no footer.
- **Number formats.** Samples, `inv_var` and LLRs are raw integer fields, not `FixedField`s;
  their fixed-point scaling is in the descriptions only.
- **TLAST on headers.** It is not checked: their length is fixed by the schema (decision 8).
- **Queued commands in error scenarios.** They keep sending commands after the bad one, as a
  host with commands in flight would.  For BAD_PARAM the host sends the full 1025-sample burst,
  per frame F4.
- **Throughput.** "One sample per clock while samples are streaming" is read as II = 1 in the
  sample loop.  The fixed per-command overhead (about 15 cycles) is not counted against it.
- **Random samples.** "nsamp = 1024 with random samples" uses noisy 16-QAM points plus 64
  full-range samples, so that LLRs both inside and at the saturation limits are exercised.
  inv_var is drawn from the fixed seed.
- **Inverse noise variance of 0.** This case is exercised in `unknown_cmd_fresh`, so the four
  required scenario types stay as the prompt lists them.
- **Stage 1 review stop.** The frame's process asks to stop after Stage 1 for review.  This
  session was non-interactive and the request was to build, simulate and synthesize end to end,
  so I carried on.  The Stage 1 artifacts were not changed after Stage 2 began:
  - schemas and `qam16_llr_eval`;
  - `scenarios.py`;
  - `layout.md`;
  - `check_eval.py`.
- **Report file.** The frame's criteria table is in `results/report.md` (frame F8).  This file
  is the full report the prompt asks for.
- **Second co-simulation run.** Changing the timing model in `qam16_llr.py` marks the whole
  build graph stale, so run 2 re-ran synthesis and the single all-scenario co-simulation.  The
  kernel was unchanged, and every Vitis number was identical to run 1.  "Run co-simulation
  once" is read as one testbench run per build covering every scenario.

## Open Items

- **Timing model fitted to one point.** `proc_ii` = 1 comes from synthesis.  `proc_latency` = 11
  was set from one co-simulated command (nsamp = 1024), not fitted across command lengths.
  Short commands were not compared against pysim.
- **Missing TLAST in pysim.** pysim cannot express a missing TLAST, so `no_tlast` runs only
  through the model, csim and cosim.
- **nsamp = 0 and 65535.** These are checked against BAD_PARAM only in the Python model
  (`results/eval_check.txt`).  The hardware runs test 1025.
- **Unused scaffold scripts.** `qam16_llr_calibrate.py`, `timing_analysis.py` and
  `qam16_llr_figures.py` belong to the reference's calibration and docs-figure flow.  This build
  does not import or run them.  I could not delete them because file deletion was not
  permitted in this session.
- **Files to commit.** Reviewers need the evidence files committed together:
  - `w32_proj/solution1/syn/report/`;
  - `w32_proj/solution1/sim/report/`;
  - `data/w32/`;
  - `results/`.
- **No csim log.** The csim stage's Vitis log was not kept: the synthesis stage reopens
  `w32_proj` with `-reset`.  The csim evidence is the recorded outputs in
  `data/w32/*/csim/`, checked in `results/check_csim.json`.
